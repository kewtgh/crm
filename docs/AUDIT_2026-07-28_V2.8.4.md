# Lumina CRM v2.8.4 全面审计

> **Archived / obsolete production architecture:** this point-in-time audit predates the v3.7
> Docker Compose deployment. Use `docs/DEPLOYMENT.md` for current production operations.

审计日期：2026-07-28
审计范围：认证与会话、部署控制器与 runner、systemd、运行环境、readiness、Worker/队列、
数据库契约、业务边界、UI/UX、可访问性、测试、发布文档与版本一致性。

## 结论

现有应用的 workspace/RLS、AAL2、部署锁、原子切换、失败恢复、forward-only migration、
回滚状态和 release 保留架构可以继续使用，不需要重写。v2.8.4 需要修复四项发布阻断和两项
产品完整性问题：

1. Lumina 生产运行与部署 runner 仍被强制绑定到本机 ProxyAgent/v2rayA。
2. “记住设备”错误地兼任 session 持久化开关，未勾选及 SSO 登录不能保证 30 天 refresh
   session。
3. readiness 对 Supabase 只给 3 秒共享超时，并把 Auth、数据库、Worker、队列异常折叠为
   同一个依赖错误。
4. 数据库 readiness 把 missing worker 重复计入 `staleWorkers`，无法准确解释 Worker 原因。
5. 登录帮助邮箱仍是旧地址且不可点击。
6. 多处已渲染文本为 8–11px，与项目自己的 Chromium 验收下限和部署指引不一致。

## 发现

### P0 — OPS-01 运行阶段默认依赖代理

- `lumina-crm-deploy.service` 注入 `LUMINA_HTTPS_PROXY` 和代理 preload `NODE_OPTIONS`。
- runner 启动时强制要求这两个值，`safeBaseEnvironment()` 还会把系统代理变量传入 npm、
  检查、构建、迁移和公网 health。
- `assertSystemdRuntime()` 要求 Web/Worker 带代理，部署资产测试也把代理当作正确状态。
- 文档要求保留 runtime ProxyAgent drop-in，重启后 Lumina 无法独立于 v2rayA 建立已验证状态。

影响：代理停机或配置变化会扩大为 CRM Web、Worker、readiness 和部署失败，并有把代理环境
泄漏到 npm、Supabase CLI 或构建子进程的风险。

修复方向：systemd 显式清除代理环境；runner 生成无代理子进程环境；只允许
`git -c ... pull --ff-only origin main` 的单次 GitHub 拉取携带临时 Git 配置。不得写
global/local Git config，不改 HunterAI、v2rayA 或其他服务器服务。

### P0 — AUTH-01 session 寿命由“记住设备”意外控制

共享 cookie helper 只有 `persistent=true` 才设置持久 refresh cookie。密码登录、设备 OTP、
MFA 和 SSO 分别传递 `remember` 或 `false`；因此未勾选及 SSO 是浏览器会话，而不是至少 30
天。checkbox 的可见文案已经是“记住此设备”，不应再隐式改变登录 session 寿命。

修复方向：所有成功认证路径统一写入 30 天 HttpOnly refresh/persistence cookie；checkbox
只控制可信设备/MFA 记忆。refresh rotation 始终保持同一期限，登录页明确告知 session 策略。

### P0 — OPS-02 readiness 超时和失败归因不准确

Auth health 与数据库 RPC 共用一个 3 秒 `AbortController` 和 `Promise.all`。任一路径超时或
拒绝后，响应把 Auth、数据库、Worker、队列全部标为失败，只返回
`DEPENDENCY_UNAVAILABLE`。部署 runner 对 503 只记录 HTTP 状态，看不到安全的组件错误码。

修复方向：Supabase 检查各用 10 秒边界并用 `Promise.allSettled` 独立收敛；保留既有布尔
`checks` 契约，同时增加稳定的组件状态/原因；数据库不可用时将 Worker/队列标为 blocked，
而不是伪报它们自身失败。部署 readiness 单次 HTTP 边界提高到 15 秒并记录稳定原因码。

### P0 — DB-01 missing/stale Worker 重复计数

`service_readiness_snapshot_for_workers` 先统计 stale，再执行
`stale_workers := stale_workers + missing_workers`，最后同时返回两个字段。一个缺失 Worker
会显示 `missingWorkers=1`、`staleWorkers=1`。

修复方向：新增 forward-only migration，在不破坏 RPC 名称、参数、权限和旧客户端的前提下
把 missing 与 stale 分开；增加 pgTAP 回归。

### P1 — UX-01 登录帮助信息过期

中英文 `auth.help` 都包含旧的 `support@lumina-edu.com`，而且是纯文本；产品帮助中心也仍
硬编码同一旧地址。

修复方向：登录页和帮助中心统一改为用户指定的 `support@ewaya.comm`，使用 `mailto:`，
并保留中英文提示。

### P1 — UX-02 可读性基线与门禁冲突

`globals.css` 和 `v220-quality.css` 中存在大量 8、9、10、11px 文本。浏览器 QA 会把任何可见
直接文本小于 12px 记为错误，部署指引也明确要求无低于 12px 正文。当前只把 `small` 覆盖到
11px，仍然不满足契约。

修复方向：把应用/auth 可见文本声明的 8–11px 机械提升为 12px；保留标题和数据大字号，
再用 1440/1024/375 Chromium 检查溢出、对比度和交互。

### P1 — TEST-01 部署测试固化了错误代理架构

部署单测和源码契约要求 ProxyAgent 存在，并仍断言 `fetch + merge --ff-only`，没有验证：

- 临时 Git 配置仅用于一次 `pull`；
- npm/build/migration/health 环境不含代理；
- systemd 重启不依赖 v2rayA；
- readiness 原因分类和 session 默认 30 天。

修复方向：把上述项目变成可执行单元/源码/pgTAP/Chromium 契约。

## 架构与业务逻辑复核

- workspace membership、RLS、capability、AAL2 与 service-role 边界未发现需要放宽之处。
- 部署继续保留 source clean、固定 origin/branch、`pull --ff-only`、明确 SHA、detached
  worktree、原子 symlink、forward-only migration、失败恢复和应用回滚；禁止 reset、force、
  rebase 与隐式 merge。
- Worker enable flag、失败心跳、租约、failed/stuck queue、隐私/审批/通信幂等契约保持。
- 不引入会修改生产外部状态的自动修复；readiness 只报告和给出可执行建议。
- 本轮不执行生产部署，也不修改/停止服务器 v2rayA、HunterAI、Cloudflare、Docker 或
  PostgreSQL。

## 本版本引入的完整增强

本次审计筛选出的可安全落地新能力全部进入 v2.8.4：

1. 结构化 readiness 组件状态与稳定失败原因。
2. 30 天默认 session 策略和登录页可见说明。
3. 临时 GitHub pull 代理边界及无泄漏资产检查。
4. missing/stale Worker 精确遥测。
5. 可点击支持邮箱。
6. 全局 12px 可读性基线。

需要真实 IdP、邮件供应商、备份、Supabase production 或服务器权限的事项属于上线验收输入，
不能在源码中伪造为新功能或已完成状态。
