- 审计日期：2026-07-29
- 审计基线：`936ccc9 feat: release v3.2.0 delivery integrity`
- 基线版本：3.2.0
- 审计范围：应用架构、认证授权、API、PostgreSQL/RLS、业务一致性、Worker/部署、
  UI/UX、响应式、可访问性、国际化、测试、依赖与发布资料

## 1. 结论

v3.2.0 的自托管 PostgreSQL、应用自有认证、分角色数据库访问、RLS、对象存储、Worker、
备份恢复、可重试预约和消息幂等基础仍然成立。本轮没有发现 P0、认证绕过、跨 workspace
直接写入、明文认证密钥、危险 HTML 注入、遗留托管平台运行依赖或已知 npm 漏洞。

新的高价值缺口集中在沟通收件箱的“本地闭环”和增长边界。当前发送请求虽然使用稳定消息
键和供应商幂等头，但相同请求键在数据库已经标记成功后重放，应用仍会再次调用供应商。
新建会话也只有客户端同步锁，没有数据库请求指纹。读取路径虽然会报告 100 个会话上限，
却为每个会话聚合全部历史消息，响应大小仍会随业务历史无界增长；搜索状态下执行写操作后，
POST 又返回未过滤的默认快照，当前搜索结果与总数可能短暂失真。

本轮以“分页读模型、写入幂等和重放不产生外部副作用”为 v3.3.0 的产品增强，不扩张新的
大型业务域。

## 3. 审计发现

### P1-COM-01：成功消息重放仍会再次调用供应商

`queue_communication_message` 在同键同负载时返回既有消息，但 API 无条件调用 `deliver`。
因此数据库已是 `SENT` 的请求重放仍会产生一次新的供应商请求。本地业务状态足以判断
“不应再次投递”，不应只依赖真实供应商是否兑现 `Idempotency-Key`。

### P1-COM-02：新建沟通会话没有端到端幂等

消息页面有同步 `operationLock`，但 `create_communication_thread` 没有请求键和负载指纹。
如果数据库已经提交而响应丢失，用户重试会创建重复会话。客户端互斥不能覆盖网络结果不确定
或多个浏览器标签页。

### P2-COM-03：收件箱响应仍随全部消息历史无界增长

`communication_inbox_snapshot` 最多选择 100 个会话，却为每个入选会话聚合全部消息。
这同时放大数据库相关子查询、JSON 构造、网络传输、React 状态和客户端搜索成本。会话数量
截断提示关闭了“看不见更多会话”的问题，但没有关闭消息历史负载的增长边界。

### P2-COM-04：搜索状态下写操作返回错误的读模型

GET 会按当前 `q` 搜索，POST 和失败后的 `reload` 却固定调用无参数 `loadCommunications()`。
发送、记录来信、重试或创建会话后，组件会用默认未过滤前 100 条覆盖当前搜索结果；
搜索输入没有变化时，搜索 effect 不一定再次执行。结果总数、选中项和当前列表可能与输入不符。

### P3-UX-01：收件箱只有容量提示，没有可操作分页

用户命中 100 条上限后只能缩小搜索，没有上一页/下一页；单个长会话也无法分段浏览历史。
这不是单纯视觉问题，而是历史沟通的可发现性和可访问操作缺口。

### P3-MAINT-01：热点文件存在，但本轮不做无目标重写

部署 runner、数据库 gateway、历史迁移和少数组件仍较大。它们有清晰的运行边界与契约，
本轮缺陷不要求重写。新的沟通分页和投递决策应放在独立数据库函数、明确类型和小型客户端
状态边界中，避免继续依赖一个“全量快照”。

## 4. 纳入 v3.3.0 的修复与产品增强

1. **会话创建幂等**：客户端为未修改的新会话草稿复用请求键；PostgreSQL 保存规范化负载
   指纹，同键同负载返回原会话，同键异负载明确冲突。
2. **投递所有权闭环**：消息入队 RPC 返回本次调用是否拥有投递权；已成功、已失败或仍在
   有效尝试窗口内的重放不再次调用供应商，超出安全窗口的遗留 QUEUED 消息才可重新取得
   投递权。
3. **真正分页的收件箱**：数据库只返回当前页会话摘要与精确总数，API 校验页码和每页数量，
   UI 提供上一页、下一页、页码和每页数量。
4. **分页消息历史**：选中会话单独加载固定大小的消息页，默认显示最新页，可浏览较早记录，
   不再把全部会话的全部消息装入一个响应。
5. **一致的写后刷新**：POST 返回最小动作结果；客户端按当前搜索、页码和选中会话刷新，
   创建后明确定位新会话，不再用默认快照覆盖筛选状态。

## 5. 不纳入本轮的条件性扩张

不在缺少真实吞吐、供应商延迟和回执数据时把同步邮件路径整体改造成新队列基础设施。现有
Worker 模型可在生产数据证明需要时承接异步投递；本轮先关闭当前同步路径可由仓库独立证明的
重复副作用和读取增长问题。外部供应商仍需在生产接入时验证幂等合同。

## 6. 外部边界

实际 VPS/Caddy/systemd 安装、DNS/TLS、真实邮件/IdP/SCIM/连接器凭据、供应商幂等合同、
独立备份生命周期、恢复演练和代表性容量测试仍是生产激活门禁，不是仓库代码可以替代的
完成项。
