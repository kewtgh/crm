# Lumina CRM v2.6.0 完整审计

- 审计日期：2026-07-27
- 审计基线：`0214991 feat: update Weiai branding and release v2.5.1`
- 范围：安全、业务不变量、架构、发布溯源、国际化、UI/UX、可访问性、响应式体验与产品能力
- 方法：源码反查、现有迁移/契约/浏览器证据复核、TypeScript、ESLint、Node 契约、依赖审计和运行边界检查

## 结论

v2.5.1 没有发现直接权限提升、数据丢失、公开注册绕过或已知依赖漏洞。TypeScript、ESLint
通过，`npm audit` 为 0；既有固定 Chromium 报告记录 78 个页面/视口且无 UI 错误。

初审确认 2 个 P1、5 个 P2 和 5 个 P3；执行期的最新依赖元数据复查又发现 1 个供应链 P1。
最重要的问题不在“页面能否打开”，而在用户偏好会
影响日历与 Worker 的运行完整性、浏览器证据无法完整证明对应源码状态，以及紧凑界面中若干
操作仍缺少一致的防误触与可访问语义。

## 已确认问题

### P1（执行期新增）：最新供应链公告令原有“0 漏洞”结论失效

完整发布门禁重新查询注册表时发现 `react-server-dom-webpack` 19.2.6、PostCSS 8.5.14 和
旧 `brace-expansion` 依赖链已命中新的 high 公告，共计 14 条路径。`npm audit fix --force`
给出的 Next 9/ESLint 10 组合会分别造成框架倒退或与现有 React 插件真实崩溃，不能机械采用。
整改必须升级 React/RSC 与 PostCSS，并为仍依赖旧 minimatch 函数 API 的 Next Lint 插件提供
使用安全 5.0.8 实现的窄兼容层；审计、ESLint 与双 API 契约须同时通过。

### P1：不受约束的时区可破坏日历、提醒与页面格式化

`PATCH /api/settings` 只要求 `timezone` 是 1–60 字符字符串，数据库
`user_preferences.timezone` 也没有时区约束。畸形值可进入：

- 浏览器 `Intl.DateTimeFormat`，触发 `RangeError` 并令工作区渲染失败；
- `listAppointments` / `zonedToUtc`，令日历读取或保存失败；
- PostgreSQL `now() at time zone preference.timezone`，令提醒 Worker 的批次事务失败。

客户端虽然只显示五个选项，但 API/RLS 不能把客户端控件当成数据不变量。

### P1：不存在的 DST 本地时间会被静默改写

客户端和服务端各自复制了一套“迭代猜测”时区转换。对于
`America/New_York` / `Europe/London` 夏令时跳时区间内不存在的本地时间，算法没有做
往返校验，可能把用户输入静默排到另一个时间。合同续约、付款、活动和日历均复用该转换。

### P2：认证语言偏好不跨设备一致

顶栏语言开关只更新 React、Cookie 和 LocalStorage；`user_preferences.locale` 只有在设置页
提交整张账号表单时才更新。CRM 布局虽然已经读取用户偏好，却没有把已保存语言同步给根
国际化上下文。结果是新设备登录、清 Cookie 或从设置页外切换语言后，数据库偏好与当前界面
互相漂移。

### P2：v2.5.1 浏览器证据缺少源码状态溯源

现有 `work/browser-qa-chromium-1228/report.json` 显示 `appVersion=2.5.1`，但
`gitSha=ab7233c`（v2.5.0）。这是在提交品牌更新前对工作树构建并运行 QA 的结果，不代表
浏览器本身失败；问题在于报告只记录 HEAD 和 build hash，没有记录工作树是否有修改、源码
指纹或差异状态，文档却容易把它解释为“精确 commit 证据”。

### P2：品牌更新没有进入真实资源门禁

`check-production-assets.mjs` 只从 `/login` 与 `/privacy` 提取 CSS/JS。v2.5.1 新增 Logo、
16/32/192 Favicon 和 OpenGraph 资源，但契约只检查文件存在与源码字符串，不验证真实生产
HTTP 状态、MIME、PNG 签名、重定向和元数据引用。品牌资源损坏仍可能在门禁全绿后上线。

### P2：破坏性操作的确认模式不一致

学生监护人、家庭成员和升学批次使用阻塞式 `window.confirm`；日历取消、门户邀请撤销、
保存视图删除等图标操作则可能直接执行。原生确认不可统一双语样式和焦点管理，直接执行又
增加误触风险。项目已有可访问抽屉基础，但缺少轻量、复用的 `alertdialog`。

### P2：有界进程契约依赖真实子进程，受限环境诊断失真

36 条 Node 契约中 35 条通过；“静默子进程应被终止”在当前受限 Windows 环境无法创建嵌套
子进程，测试最终只断言到 `undefined\nundefined`，没有验证 watchdog。运行器本身正确上抛
`EPERM`，但契约不可注入进程工厂，既不确定也难以单元测试。

### P3：导航、404 与重复提交存在低级体验缺口

- 404 是硬编码的“中文标题 + 英文说明 + 中文按钮”，不跟随中英文目录。
- 侧栏和设置标签的当前项主要依赖颜色，缺少一致的 `aria-current="page"`。
- 仪表盘任务完成按钮在请求期间不禁用；快速双击会发送两个请求并把聚合数减两次。
- 国际化写 LocalStorage 未做异常隔离；存储被禁用时可留下已切换但未刷新的半完成状态。
- `v200-workspaces.tsx` 继续承担多个业务工作区；本轮应至少把通用时间和确认逻辑抽出，避免
  再向大组件复制基础设施。

## 产品与工程扩展建议（纳入本轮）

1. **页面 + 记录统一命令搜索**：扩展 Ctrl/⌘K，让结果同时包含当前角色可访问的模块页面和
   业务记录；页面结果应即时出现，远程记录加载不得遮住它们。
2. **跨设备偏好同步**：顶栏切换语言时保存最小偏好，登录后以服务端偏好恢复语言；保持公开
   页面无需登录即可切换。
3. **安全操作确认层**：提供双语、可聚焦、Escape 可关闭、焦点恢复的 `alertdialog`，逐步统一
   删除、撤销、归档和取消类操作。
4. **可复验发布证据**：浏览器报告记录源码状态/指纹，生产资源门禁验证品牌图片与元数据，
   明确区分“干净 commit”与“已验证工作树”。
