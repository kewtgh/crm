## 1. 结论

v3.3.0 的认证授权、PostgreSQL/RLS、对象存储、迁移校验、沟通分页与幂等基础保持成立。
本轮没有发现 P0、认证绕过、未分类写端点、真实秘密入库、危险 HTML 注入或已知 npm
漏洞。类型检查、lint、31/31 核心契约、5/5 CAPTCHA 契约和 69 个迁移校验均通过。

新的高价值缺口集中在后台投递的时间边界。通知 outbox 是唯一没有外部请求 timeout 的生产
Worker；通知与日历投递虽然有数据库租约和稳定任务键，却没有把稳定键发送为标准
`Idempotency-Key` 请求头。更根本的是，systemd 给整个 Worker cycle 4 分钟，但 6 类 Worker
当前串行运行：仅默认通知与日历批次的外部等待上界就可能超过 4 分钟，启用集成同步后更
明显。合法运行可能被 systemd 中止，租约到期后再领取，从而放大重复副作用风险。

错误态体验还有两个低风险但明确的缺口：CRM loading 的屏幕阅读器文本固定为英文；根级
致命错误页固定为中文。员工创建对话框允许在请求未确定时用 Escape/取消关闭，并在输入
修正后继续保留陈旧 `aria-invalid` 状态。

## 3. 审计发现

### P1-OPS-01：通知 outbox 外部请求没有 timeout

`scripts/process-notification-outbox.mjs` 的邮件 Webhook `fetch` 没有 `AbortSignal.timeout`。
供应商连接悬挂会阻塞整个批次；数据库 5 分钟租约到期后，另一个 cycle 可以再次领取，形成
并发不确定投递。其他外部 Worker 已有 20–60 秒边界，通知 Worker 是不一致的遗漏。

### P1-OPS-02：稳定任务键没有进入供应商幂等协议

通知 outbox 使用 `job.id`，日历投递使用 `idempotency_key`，但两条请求都没有
`Idempotency-Key` header。供应商已接收而响应丢失时，数据库只能安全重试本地状态，不能
阻止外部重复副作用。沟通消息链路已正确使用标准 header，可作为统一合同。

### P1-ARCH-03：串行 Worker cycle 与 4 分钟服务上界不相容

`process-worker-cycle.mjs` 逐个等待 6 类 Worker。默认通知和日历各 20 条，单条投递最多
20 秒；启用集成同步后单条最多 60 秒。串行最坏等待明显大于 systemd 的 4 分钟
`TimeoutStartSec`。仅延长 timeout 会降低卡死可见性；应让相互独立的 Worker 类别并行，
每类内部使用受限并发，并限制生产批量配置，使默认外部等待上界保持在服务预算内。

### P2-UX-04：关键错误/loading 状态没有完整国际化

`app/(crm)/loading.tsx` 固定播报 `Loading`，中文界面屏幕阅读器会收到英文；
`app/global-error.tsx` 脱离根布局后只显示中文，英文用户在最严重的错误状态下失去可理解反馈。

### P2-UX-05：员工创建对话框允许不确定提交期间关闭

创建请求 pending 时关闭按钮、取消按钮与 Escape 仍可关闭 native dialog，但 mutation 不会
取消。请求稍后成功或失败时，视觉状态与实际账户状态可能让管理员困惑。字段错误也不会在
用户修改对应输入时清除，`aria-invalid` 会一直保留到再次提交。

### P3-MAINT-06：Worker 安全策略分散

各 Worker 分别实现批量循环、并发、timeout 和 delivery headers，已经出现行为漂移。本轮
应新增小型、可单元测试的受限并发与邮件投递 helper；不重写数据库 gateway 或历史迁移。

## 4. 本轮纳入的修复与产品增强

1. **统一邮件投递合同**：通知与日历 Worker 使用稳定 `Idempotency-Key`、JSON content type、
   可选 Bearer token 和明确 timeout；非 2xx 继续进入现有租约失败/退避路径。
2. **有预算的 Worker cycle**：独立 Worker 类别并行运行；外部任务在每类内部按小并发上限
   处理；配置校验限制 batch/concurrency，避免合法配置突破 4 分钟默认预算。
3. **可验证的运行时保护**：对并发上限、结果顺序、投递 header、timeout 与过大 batch 拒绝
   增加 v3.4 行为契约。
4. **错误态体验完整性**：loading 使用现有 i18n Provider；global error 提供带语言标记的
   双语兜底；员工创建 pending 时阻止关闭，并在字段修改时清理陈旧错误。

## 5. 不做伪修复的边界

仓库中多个日期型业务规则使用 PostgreSQL `current_date`，而用户可设置显示时区。单独修改
合同列表会使合同摘要、报价有效期、逾期回款与列表互相矛盾。完整方案需要明确 workspace
级业务时区、迁移现有 workspace、统一数据库业务日并由产品确认跨时区规则；本轮把它记录为
架构决策门禁，不把用户个人显示时区偷偷替换成全组织业务规则。

真实邮件供应商仍需在生产环境验收 `Idempotency-Key` 合同；VPS/Caddy/systemd、DNS/TLS、
真实 IdP/SCIM、独立备份生命周期和代表性容量测试仍是外部上线门禁。
