# Lumina CRM v3.2.0 全项目审计

- 审计日期：2026-07-29
- 审计基线：`4546f96 feat: harden CRM v3.1 integrity and deployment`
- 基线版本：3.1.0
- 审计范围：应用架构、认证授权、API、PostgreSQL/RLS、业务真实性、Worker/部署、
  UI/UX、可访问性、国际化、测试、依赖与发布资料

## 1. 结论

v3.1.0 的自托管 PostgreSQL、应用自有认证、分角色数据库访问、RLS、对象存储、Worker、
备份恢复和部署边界仍然成立。本轮没有发现需要推翻现有架构的 P0，也没有发现公开注册、
认证绕过、跨 workspace 直接写入、明文认证密钥、危险 HTML 注入或已知 npm 漏洞。

当前最高风险集中在两个真实业务动作的“失败不安全”和“结果不确定”：损坏的日历更新请求
会默认执行完成动作；新建预约只依赖 React 提交锁，网络超时后的重试仍可创建重复预约。
沟通收件箱也存在同源问题：浏览器超时短于服务端供应商请求上限、快速重复提交会产生不同
请求键、供应商请求没有显式幂等键。此外，收件箱静默截断 100 个会话，人工截图复核还发现
搜索框重复显示两个搜索图标。

本轮不扩张新的大型业务域，而把“业务动作可重试、结果可证明”作为 v3.2.0 的产品增强。

## 3. 审计发现

### P1-CAL-01：损坏的日历 PATCH 请求会默认完成预约

`app/api/calendar/[id]/route.ts` 在 `request.json()` 失败时使用
`{action:"COMPLETE"}` 作为回退值。空请求体、截断 JSON 或错误 Content-Type 不应产生任何
业务副作用；现状却能通过 Zod 并执行 `completeAppointment`。这是失败不安全的状态转换。

### P1-CAL-02：预约创建没有端到端幂等

日历 UI 已有同步 `useRef` 锁，可以挡住同一事件循环的双击，但 API 和 PostgreSQL
`create_appointment_with_delivery` 没有请求键。若数据库已经提交而响应丢失，用户重试会创建
第二条预约、第二组参与人和第二组投递任务。客户端互斥不能替代服务端/数据库幂等。

### P1-COM-01：沟通投递的超时与幂等边界不闭合

通用 `apiFetch` 默认 15 秒超时，而沟通 API 允许供应商 `fetch` 持续 20 秒。浏览器可能先
报告失败，服务端随后却成功，形成不确定结果。消息编辑器只依赖异步 React `pending`，
快速双击可生成两个不同 UUID；供应商请求也没有显式 `Idempotency-Key`。虽然数据库已有
消息请求键，同一业务意图仍可能被作为两个意图或两个供应商请求执行。

### P2-COM-02：沟通收件箱静默截断 100 个会话

`communication_inbox_snapshot` 固定最多返回 100 条，但只返回数组，不返回匹配总数或
`truncated`。UI 无法告诉用户“没有更多会话”还是“有更多但未展示”。对长期使用的 CRM，
这会造成历史沟通不可发现。

### P3-UI-01：沟通搜索框重复渲染搜索图标

`SearchField` 已内置搜索图标，消息页又在外层渲染一个 `Search`。桌面和 375px 截图均可见
两个相邻图标，属于低级但明确的视觉缺陷。

### P3-MAINT-01：热点文件仍偏大，但不宜无目标重写

部署 runner 约 900 行，数据库 gateway 与少数组件/仓储约 400–500 行。边界仍可测试，
本轮缺陷不要求重写它们。新幂等规则和请求策略应放在小模块或独立迁移中，避免继续把纯规则
塞进页面组件。

## 4. 纳入 v3.2.0 的产品增强

1. **可安全重试的预约创建**：浏览器为同一未修改草稿复用请求键；PostgreSQL 保存请求键和
   规范化负载指纹，同键同负载返回原预约，同键异负载明确冲突。
2. **失败不产生动作的日历更新**：无法解析或不符合 schema 的请求统一返回 400，永不推断
   `COMPLETE`。
3. **可证明的沟通投递意图**：同一未修改消息草稿复用请求键，所有沟通操作使用同步互斥，
   供应商请求携带消息 ID 作为幂等键，并让服务端外部请求上限小于浏览器上限。
4. **可见的收件箱容量**：数据库返回 `items`、`total`、`truncated`，UI 在结果被截断时
   明确提示用户缩小搜索范围。

## 5. 不纳入本轮的扩张

不引入新的外部 AI 自动执行、新 CRM 业务域或第二套消息基础设施。真实供应商是否支持幂等
请求头必须在生产接入验收中确认；若未来消息量要求完全异步投递，可在代表性吞吐与重试策略
明确后，把沟通消息纳入现有租约 Worker 模型。本轮先关闭当前同步路径中可证明的超时和重复
执行缺口，不伪造外部供应商能力。

## 6. 外部边界

实际 VPS/Caddy/systemd 安装、DNS/TLS、真实邮件/IdP/SCIM/连接器凭据、供应商幂等合同、
独立备份生命周期、恢复演练和代表性容量测试仍属于生产激活门禁，不是仓库代码可以替代的
完成项。

本审计识别的 P1/P2/P3 仓库内缺口已全部纳入 v3.2.0 计划并完成。实现后复查没有发现遗漏、
半完成项目或新增同源回归；验证命令、浏览器证据和仍保留的外部门禁记录在
`FINAL_REAUDIT_2026-07-29_V3.2.0.md`。
