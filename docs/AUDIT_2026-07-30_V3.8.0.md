# Lumina CRM v3.8.0 全项目与 v3.7 架构增量审计

- 审计日期：2026-07-30
- 审计基线：`ecfef8b feat: isolate production with Docker Compose`
- 基线版本：3.7.0
- 审计范围：v3.7 Compose/发布架构、宿主权限、备份恢复、认证/API、PostgreSQL/RLS、
  Worker、业务规则、共享 UI/UX、响应式、可访问性、国际化、测试和发布资料

## 1. 结论

v3.7 已经正确建立固定 Compose project、内部数据库网络、外部持久卷、Web/Worker/运维
凭据分离、不可变 commit image、前向迁移、应用镜像回滚、Cloudflare origin 认证和
Lumina 标签化清理。现有 TypeScript、ESLint、47 个业务/安全合同和依赖审计均通过；未发现
新的认证绕过、SQL 注入、RLS 逃逸、未签名 webhook、生产 TODO/FIXME 或已知 npm 漏洞。

但“共享宿主隔离”这一最高层目标尚未成立。`lumina-crm` 宿主用户和 systemd 服务直接连接
rootful Docker daemon；Docker socket 可以启动任意 bind-mount/container，等价于宿主 root。
Compose 名称、标签和清理 allowlist 只能防止正常运维误操作，不能隔离已被利用的部署账号，
因此也不能保护同机 HunterAI、Temporal 或宿主文件系统。

v3.7 还遗留了一个已失效的宿主 release 路径磁盘 timer、只验证数据库而不验证同批对象归档
的 restore-test，以及一个实际被 CSRF 防线拒绝的个人菜单退出动作。它们均需在首次生产部署
前关闭。

## 3. 审计发现

### P0-ARCH-01：rootful Docker socket 使共享宿主隔离失效

`lumina-crm.service`、deploy、backup、restore 和 storage maintenance 均依赖系统
`docker.service`。部署用户必须能直接执行 Docker/Buildx/Compose；获得该账号执行能力后，
即可绕过所有 Lumina 标签检查并控制共享 daemon 的任意容器、卷和宿主 bind mount。

**整改方向：** Lumina 必须使用由 `lumina-crm` 用户拥有的 rootless Docker user service，
固定 `DOCKER_HOST=unix:///run/user/<lumina uid>/docker.sock` 和独立 data root。rootful daemon
可继续服务其他项目，但 Lumina unit、CLI、builder 和维护程序不得连接它。发布门禁同时验证
Docker `SecurityOptions` 包含 rootless、cgroup driver 为 systemd、data root 精确匹配。

### P1-OPS-02：Compose 改造后磁盘监控 timer 已失效

`lumina-crm-disk-monitor.service` 仍进入已删除的 `/opt/lumina-crm/current`；脚本默认监控
宿主 `/var/lib/postgresql`，而 v3.7 数据已进入 Docker volume/rootless data root。timer 在
新主机上会在开始检查前失败，不能提供告警。

**整改方向：** 工作目录改为 `/opt/lumina-crm/source`，部署环境明确配置 root、Lumina
rootless Docker data root 和 deployment state 路径；阈值必须拒绝 NaN/越界值。

### P1-DR-03：对象归档没有进入恢复验证

`BACKUP_LOCAL_OBJECTS=true` 时会生成并上传同时间戳的加密 tar，但 restore-test 只选择
`.dump.enc`。数据库恢复成功不能证明合同/导出/头像等对象字节可解密，也不能发现同批对象
归档缺失。

**整改方向：** restore-test 按数据库时间戳定位配套 `.objects.tar.enc`，在要求本地对象
备份时 fail closed，执行 AEAD 解密和只读 tar listing 校验，不提取或覆盖生产对象。

### P1-UX-04：个人菜单“安全退出”被 CSRF 防线拒绝

个人菜单使用原生 `<form method="post">`。会话 cookie 存在时服务端要求
`x-csrf-token === crm_csrf`；HTML form 无法添加该 header，因此退出返回 403。用户仍留在
已登录页面，且菜单没有错误或 pending 状态。

**整改方向：** 使用统一 `apiFetch` 发起 JSON/204 退出，服务端保留 redirect 兼容路径；
按钮提供 pending、错误反馈和定向 Chromium 回归。

### P2-MAINT-05：v3.6 发布内核与测试仍混在当前架构

生产 controller 只使用路径、请求文件和状态分类等少量函数，但共享 core 仍包含 release
目录、current symlink、宿主 Web/Worker systemd 和旧 storage policy。部分未调用的资产校验
甚至要求“runner 不接触 Docker”，与 v3.7 实际模型冲突。测试通过并不代表这些旧断言验证
了当前发布路径。

**整改方向：** 删除未被生产路径使用的历史 core，把 deploy tests 改为 rootless
Compose、当前状态机、镜像清理、凭据和恢复合同；历史事实只保留在归档文档/Git。

### P2-OPS-06：备份保留配置可静默变成无效值

`BACKUP_RETENTION_DAYS` 使用 `Math.min/Math.max(Number(...))`；非数字会得到 NaN 并在通知
JSON 中变成 `null`。本地加密副本固定保留 48 小时，却没有独立配置或文档说明。

**整改方向：** 对远端生命周期声明和本地短期保留使用严格整数边界；新增显式
`BACKUP_LOCAL_RETENTION_HOURS`，并说明远端删除仍由对象提供方 lifecycle 执行。

### P2-UX-07：共享搜索和进度组件有短暂陈旧/非法显示

全局搜索在新查询防抖期间继续展示上一查询的记录结果；`ProgressBar` 虽把宽度/ARIA 夹在
0–100，默认文本仍显示原始负数或大于 100 的值，NaN 还会产生非法样式。

**整改方向：** 查询改变即清除旧记录结果；进度值先做 finite + 0–100 归一化，并统一视觉、
文本和 ARIA。

## 4. 本轮纳入的修复与可执行业务/运维增强

1. **Lumina rootless Docker 隔离**：让部署账号即使失陷也不能控制 rootful 共享 daemon。
2. **rootless 发布门禁与诊断**：发布和维护同时验证 socket、rootless、cgroup 和 data root。
3. **同批数据库 + 对象恢复验证**：把对象归档从“已上传”提升为“本地可恢复证据”。
4. **可配置的短期本地备份保留**：严格配置、明确远端 lifecycle 责任。
5. **可靠退出会话交互**：CSRF 正确、pending/错误可见、浏览器可回归。
6. **当前架构测试内核**：移除与 v3.7 冲突的死代码和静态安全错觉。
7. **共享 UI 一致性修复**：搜索和进度组件不再显示陈旧或非法状态。
8. **生产镜像最小脚本集**：只复制 Web/Worker/迁移/备份入口实际需要的脚本，移除 QA、
   部署 controller 和 smoke 工具。

不新增缺少真实需求和数据闭环的 CRM 模块。现有行动中心、客户 360、自动化、隐私、
集成、导出和运营中心已经覆盖近期产品方向；本轮新增能力集中在首次上线前的隔离与可恢复性。

## 5. 外部边界

仓库可以交付 rootless 安装合同、unit、校验和 runbook，但不能伪造真实 VPS 的 subordinate
UID/GID、cgroup v2、rootless user service、DNS/TLS、Cloudflare、邮件/IdP、S3 lifecycle 或
真实恢复演练结果。生产操作者必须按新 runbook 配置并验证；rootful Docker 连接一律视为
发布阻断，而不是允许降级。
