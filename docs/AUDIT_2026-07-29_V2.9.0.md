# Lumina CRM v2.9.0 增量全面审计

审计日期：2026-07-29
审计基线：`9d0ad53`（v2.8.4，审计开始时工作树干净）
审计范围：认证与会话、请求来源与公开 URL、CSP、SCIM/身份补偿、业务并发、列表状态、
UI/UX、可访问性、依赖完整性、测试与发布证据。

## 结论

v2.8.4 的 workspace/RLS、capability/AAL2、Worker/readiness、部署锁与原子发布架构可继续
使用。本轮没有发现需要重写应用或放宽权限的理由，但发现 5 项高优先级完整性问题、3 项
产品/UX 缺口，以及相应测试盲区：

1. 浏览器中多个 API 同时收到 401 时会并发轮换同一 refresh token。
2. 设置页修改密码只删除 refresh cookie、保留 access cookie；用户会先看到成功，随后在
   最多一小时内随机失效，而且访问登录页仍会被旧 access token 重定向回工作台。
3. SCIM 在下游身份同步失败时按 `id` 无条件写回旧目录快照，可能覆盖已经提交的并发新版本。
4. 生产 mutation 校验仍同时信任 `request.url` 的 origin；公开链接和 SCIM `meta.location`
   也可能使用请求 Host，而不是唯一配置的应用 origin。
5. 创建员工身份后的数据库/邮件步骤失败时，Auth 删除失败会被静默忽略，可能留下可登录的
   孤立身份。
6. CSP 对任意 `*.supabase.co` 放行，但运行环境允许自定义 Supabase 域；前者过宽、后者在
   浏览器密码恢复流程中又可能被阻止。
7. 可分享的列表筛选 URL 不会响应浏览器后退/前进，URL 与屏幕状态可能不一致。
8. 登录和 SSO 可同时提交，密码恢复成功后仍可再次提交单次 Turnstile token。

## 发现

### P0 — AUTH-01 refresh rotation 缺少 single-flight

`lib/api-client.ts` 中每个失败请求都会各自调用 `/api/auth/refresh?mode=json`。仪表盘、顶部
通知和页面数据常并发请求；access token 过期时，这些请求会同时使用同一个 refresh cookie。
即使上游存在短暂复用容忍窗口，竞争响应仍会产生不确定的 cookie rotation 顺序。

影响：偶发 401、会话链被旧响应覆盖、无意义的 Auth 压力，以及难以复现的“刷新页面后掉线”。

修复：模块级 single-flight Promise；所有等待者复用一次 refresh；网络、超时和非 JSON
响应统一转换为稳定 `ApiClientError`；增加真实并发行为测试。

### P0 — AUTH-02 密码变更后的客户端和服务端状态矛盾

密码更新使用一个临时密码 grant 做重新认证，成功后删除 refresh/persistence cookie，但：

- 当前 access cookie 未删除；
- 设置页继续显示“密码已更新”，不要求重新登录；
- `/login` 会因为旧 access cookie 仍有效而跳回 `/dashboard`；
- 其他 refresh sessions 与可信设备撤销结果没有呈现给用户。

修复：密码成功后尽力执行全局 session revoke 和 trusted-device revoke，始终清除当前浏览器
全部认证/安全 cookie，并返回可核验的撤销结果；客户端跳转到登录页展示“密码已更新，请重新
登录”，若外部撤销不完整则明确要求登录后检查会话，不伪报完全成功。

### P0 — ID-01 SCIM 补偿可能覆盖并发更新

`updateScimDirectoryUser()` 的正向更新带 `version=eq.current`，但下游同步失败后的 restore
只按 `id` PATCH。若另一 SCIM 请求已经把版本 N+1 更新到 N+2，旧请求仍可把整行退回 N。
随后它还可能把旧角色/状态写回已绑定身份。

修复：restore 必须限定 workspace 和刚写入的 N+1 版本，并要求返回行；恢复旧值时版本继续
单调增加到 N+2，避免 ABA；如果版本已变化或 restore/身份复原失败，停止写旧状态并返回
稳定 `IDENTITY_COMPENSATION_REQUIRED`，交由运营处理，绝不覆盖较新的提交。

### P0 — ID-02 员工创建失败可能留下可用孤立身份

`createStaffUser()` 先创建 Auth 用户，再写 profile、membership、销售成员、审计并发送临时
凭据。后续任一步骤失败时会尝试删除 Auth 用户，但删除失败原本被忽略，调用方只会收到最初
错误，系统可能留下状态为 ACTIVE 的无完整成员关系身份。

修复：Auth 删除失败时立即尝试封禁并把元数据置为 SUSPENDED，写入
`CREATE_COMPENSATION_REQUIRED` 审计并返回稳定 `IDENTITY_COMPENSATION_REQUIRED`；不得声称
已回滚。删除成功才记录 `CREATE_ROLLED_BACK` 并传播原始错误。

### P0 — SEC-01 canonical origin 边界不唯一

生产 mutation 允许 `APP_URL` 和 `request.url.origin`。后者可能受反向代理 Host 处理影响。
密码恢复、refresh redirect、portal invitation、SSO callback 和 SCIM resource location 也
各自拼接 origin，形成多个公开 URL 决策点。

修复：新增单一 canonical-origin helper。生产只接受配置的 `APP_URL`；开发可显式回退到
请求 origin。公开 URL 和重定向统一使用 helper。`APP_URL`/Supabase URL 只允许 HTTPS
origin，或本地开发的 loopback HTTP origin，拒绝凭据、路径、查询和 fragment。

### P1 — SEC-02 CSP 上游范围与配置不一致

`connect-src`/`img-src` 固定放行整个 `https://*.supabase.co`。这比实际项目所需范围更宽，
又不能覆盖合法的自定义 Supabase 域。

修复：从已验证的 `NEXT_PUBLIC_SUPABASE_URL` 解析唯一 origin，CSP 只放行该 origin；本地
开发继续保留现有 loopback 边界。增加配置与 CSP 契约。

### P1 — UX-01 列表 URL 不是可逆状态

`usePagedResource()` 只在首次挂载读取 search params；浏览器后退、前进或同页外部 URL
变更后，筛选器、分页和 URL 会分离。

修复：监听规范化 search params，把外部历史导航同步回本地状态，同时避免自身
`router.replace` 造成循环；维持防抖、请求取消和页码纠正。

### P2 — UX-02 认证表单允许冲突或重复提交

- SSO 进行中时密码登录按钮仍可点击。
- 密码恢复邮件发送成功后按钮仍可再次提交已经消费的 Turnstile token。

修复：两条登录路径互斥；恢复成功后锁定表单提交并保留清晰状态。

## 本轮整合的新能力

以上建议全部进入 v2.9.0，不留“仅建议未实现”项：

1. 单次并发 session refresh 协调与稳定错误语义。
2. 密码安全变更回执、强制重新认证和不完整撤销提示。
3. Host-header 不可影响的 canonical public URL。
4. 精确到项目 origin 的 Supabase CSP。
5. SCIM 乐观并发补偿保护。
6. 员工身份创建的 fail-closed 补偿与可运营错误。
7. 可通过浏览器历史恢复的分享式列表视图。
8. 互斥、不可重复的认证提交状态。

真实 IdP、邮件供应商、生产 Supabase、备份、生产 unit 安装与部署仍是外部上线输入；本轮
不会伪造连接、生产验证或部署成功。
