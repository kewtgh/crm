# First principles audit for v3.46

Date: 2026-10-26. Baseline: v3.45.0 at `6708104ec6c31f1ead127f46057f8a0a625dff71`, Node 24.22.1 LTS. The existing untracked V2 audit is outside this change. Production is neither accessed nor used as a test environment.

## Principles and coverage

Settings must describe observed account facts. Failure to read devices is not an empty device list; a missing MFA count is not zero. Independent security controls must remain reachable if preference storage fails. An accepted preference change, verification-email delivery and local display update are separate outcomes. Quiet hours must preserve the actual stored interval, including a crossing of midnight, in the user's timezone. A repeated click must not launch competing account actions.

Reviewed application routing/capabilities, the recent discovery/calendar/approval/task/recovery boundaries, and traced all personal settings tabs into their API and repository owners. Examined trusted-device/session revocation, MFA reads, account email verification and reminder quiet-hour evaluation. Existing RLS, password/MFA authority, security-channel policy, token verification, financial facts and V1 recovery remain domain boundaries. This round addresses the demonstrated personal-settings defects below; it is not a new production certification or a framework rewrite.

## Findings and adopted changes

| ID | Priority | Repository evidence and impact | Adopted change |
| --- | --- | --- | --- |
| P1 | High | SettingsPage gates security and privacy on `/api/settings`, although their controls use independent APIs. The outer CRM server layout also awaits complete settings without recovery, so a client-only fix is insufficient. Retrying preferences does not restore loading; responses are accepted on settings presence alone. | Isolate security/privacy at both server shell and client workspace boundaries. Validate settings reads and cancel outdated reads. Label unavailable preference display explicitly, block local-to-UTC conversion until timezone preferences are confirmed, and recover the context after a successful validated preference read. |
| P2 | High | PrivacySettings defaults missing devices to an empty array, then invents a healthy current-browser row on empty/failure. Initial reads and post-revoke reads can overwrite each other. Device dates use the host timezone, and actions have no immediate single-writer guard. | A small dedicated device workspace validates actual API data, separates unavailable/stale/empty states, serializes reads with writes, and uses account date/time preferences. Keep accepted revocation distinct from a failed display refresh and never retry a write automatically. |
| P3 | High | The session DELETE API uses Promise.all for two independent revocations. Either failure masks an already accepted revocation, while the client presents a single generic result. | Return explicit session and trusted-device outcomes using the existing helpers. Show partial/unknown results truthfully; keep the existing current-session/current-device exclusions, authentication and CSRF policy. Do not claim transactional atomicity across the two helpers. |
| P4 | Medium | NotificationSettings offers only 22:00-08:00 and 21:00-09:00, even though storage and the reminder function support arbitrary intervals. A different existing interval cannot be accurately selected. Equal endpoints pass validation but represent an empty interval. | Add custom quiet hours using the shared compact time input, canonicalize minutes/seconds, validate paired distinct endpoints, and explain the overnight interval and timezone. Preserve the existing reminder policy and security notification requirement. |
| P5 | High | Account PATCH saves preferences before sending the verification email; a delivery failure returns a generic failure despite the saved preferences. The client merges successful saving and local language-loading failure. Copy promises notices to both addresses, but issuance targets only the new address. Fields remain editable during submission; date samples are hard-coded. | Report accepted preferences and verification delivery separately, with an unconfirmed-delivery warning and no automatic resend. Correct the email-policy description to the implemented verification flow. Freeze account/notification submissions with an immediate guard. Separate accepted saves from local display application failure. Add live timezone/date-format previews without changing the verified login email. |
| P6 | High | MFA GET converts a recovery-count failure into zero. SecuritySettings initially treats missing factors as an empty list and enables enrollment before a confirmed read. There is no explicit read retry. | Preserve a valid factor list while representing an unavailable recovery count as unknown. Validate the MFA read, expose loading/retry, gate factor actions on a current read and retain existing enrollment, verification, password and administrator rules. |

All P1-P6 fixes and the included new capabilities are adopted: independent security access, trustworthy device review/recovery, precise revocation outcomes, custom quiet hours and a live preference preview. They require no schema migration, new service, external subscription, background job or persistent parallel state system. Existing token issuance and reminder delivery policy are reused; no email is sent by development tests. Server-side settings compare-and-swap or a new authentication command ledger is not introduced without a demonstrated need and migration design.

Large cumulative components/styles remain maintenance costs. Extract the device workspace and settings contracts being changed, rather than moving unrelated business code or repeating already completed recovery work. Wider indexing, automatic customer outreach, predictive scoring and automatic financial actions are not adopted: this review establishes neither a business policy nor supporting outcome evidence for them.

## Verification boundary

Use generated fictional identities and adapter-level API fault injection, targeted tests, typecheck, changed-file lint, privacy/dependency checks, one required build and a bounded Chromium 1248 personal-settings phase. Browser fixtures use the actual components and production CSS; they are not a real database, mail-provider, Ubuntu or production test. Report unperformed checks explicitly. Keep raw reports/screenshots under ignored work/ and preserve earlier evidence.

Reference principles: [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [React effect cleanup](https://react.dev/reference/react/useEffect) and [W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html). These support explicit session lifecycle, read cleanup and accessible feedback. The findings and implementation scope above come from repository evidence, not an inferred production incident.
