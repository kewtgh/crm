# Lumina CRM v3.1.0 全项目审计

- 审计日期：2026-07-29
- 审计基线：`7e79b12 feat: migrate CRM to self-hosted PostgreSQL`
- 基线版本：3.0.0
- 审计范围：应用架构、PostgreSQL 数据一致性、认证授权、API、Worker/运维、业务流程、
  UI/UX、可访问性、国际化、测试、依赖与发布资料

## 1. 结论

v3.0.0 的自托管 PostgreSQL、应用自有认证、RLS、对象存储、Worker、备份恢复和部署边界
总体完整。修复前 TypeScript、ESLint、22 项契约测试、迁移校验、必需依赖树以及生产/完整
依赖公告检查均通过；未发现公开注册恢复、演示认证绕过、跨 workspace 表直写、明文认证
密钥或已知 npm 漏洞。

本轮发现的问题不是需要推翻架构的系统性失败，而是六个会影响数据真实性或安全边界的缺陷、
三个可维护性/体验缺口，以及适合直接纳入现有业务入口的四项增强。最高风险集中在大批量导入
的假完成状态、头像覆盖补偿、个人资料的非原子更新和公开 readiness 诊断信息。

## 3. 审计发现

### P1-IMP-01：10,000 行导入在 600 行后会被误报为完成

`components/imports-page.tsx` 允许上传最多 10,000 行，但执行端固定只调用 12 次、每次 50 行。
循环结束后没有检查最终状态，即使数据库仍返回 `PROCESSING`，UI 仍显示“已执行”。这会让
操作员把未完成批次当作完成，属于业务真实性缺陷。

### P1-STO-01：头像覆盖失败会删除旧头像

头像使用固定的 `userId/avatar.ext` 对象键。新文件先覆盖旧对象，再写数据库；如果数据库写入
失败，补偿逻辑删除该对象键，旧头像也随之丢失。对象 `put` 本身还位于补偿 `try` 之外，
元数据写入失败时可留下半写对象。

### P1-DATA-01：个人资料保存不是原子操作

姓名写入 `user_profiles`、称谓/简介写入 `user_preferences`，当前以两个独立数据库请求并行
执行。任一请求失败都可能留下半成功资料；API 返回失败却无法说明哪一半已生效。

### P1-SEC-01：详细 readiness 诊断可从公网读取

`/api/health?mode=ready` 会公开缺失环境变量名称、认证/数据库/Worker/队列状态、内部计数和
可执行修复命令。部署只需要从 `127.0.0.1:3200` 使用该详细接口，公网只需要 liveness。
现状为攻击者提供了不必要的运行时侦察信息。

### P2-CAL-01：日历查询边界使用 UTC 月初而不是用户时区月初

月视图在浏览器中使用 `Date.UTC(year, month, 1)` 作为查询边界，服务端再按用户时区显示。
在台北、上海、伦敦或纽约时区，月初/月末边界事件可能被遗漏或错误纳入。

### P2-CAL-02：新建预约缺少提交锁

日历新建表单没有 pending 状态、按钮禁用或 `aria-busy`。网络较慢时双击可创建重复预约，
而创建 RPC 没有客户端请求键可帮助消除这类重复。

### P2-CAL-03：日历固定截断 300 条且不提示

查询固定 `limit=300`，API 不返回总数或截断标记。高密度日程会静默消失，用户无法区分
“没有更多事件”和“结果被截断”。

### P2-API-01：导入 JSON 结构的字段和键数量缺少上界

批次数组有 10,000 行上界，但 `mapping`、单行 record、字段名和字段值没有相称上界。
这与前端只支持六个标准目标字段的产品约束不一致，也放大了解析和数据库 JSON 负载。

### P2-OPS-01：未捕获的 500 错误缺少安全的服务端事件

API 统一生成 request ID 和允许名单遥测，但未捕获异常本身没有与 request ID 关联的服务端
错误事件。生产中客户端能报 request ID，运维端却可能只看到通用错误码，降低定位效率。
诊断必须只包含异常类型、稳定错误码和路由模板，不能记录请求体、查询串、用户或业务记录。

### P3-A11Y-01：移动导航有焦点陷阱但未声明模态语义

移动侧栏已限制键盘焦点并支持 Escape，但展开时仍只是普通 `aside`，没有条件性的
`role="dialog"`/`aria-modal`，辅助技术对背景内容的隔离语义不完整。

### P3-MAINT-01：少数组件和样式仍是维护热点

`app/globals.css` 超过 500 行，`app-shell.tsx`、`operations-center-page.tsx`、`pipeline-page.tsx`
和 `imports-page.tsx` 职责偏多，部分文件以超长单行实现。当前边界仍可辨识，不应在业务修复
中进行无收益的全量重写；本轮只抽取新增的纯业务规则和安全判断，并用测试锁定。

### P1-DEPLOY-01：生产环境示例与运行时密钥边界冲突

部署手册要求从仓库根 `.env.example` 创建 `production.env`，但该文件同时包含迁移、数据库
管理员和一次性管理员初始化字段；实际 runner 又明确拒绝这些字段。按文档操作会让一键部署
在预检阶段失败，也增加把高权限凭据交给 Web/Worker 的风险。

### P1-DEPLOY-02：systemd 沙箱未放行持久对象目录

Web 使用 `ProtectSystem=strict` 却只放行 `/opt/lumina-crm`，Worker 没有任何对象目录写权限。
Local provider 下头像和导出对象会因 `/var/lib/lumina-crm/objects` 只读而失败；同时 Web 对
发布目录的写权限违反不可变 release 边界。

### P2-DEPLOY-01：部署预检没有验证 v3 角色和对象 provider 配套配置

原 runner 只检查三条数据库 URL 和对象 provider 非空，没有确认 URL 分别使用
`crm_app`、`crm_system`、`crm_worker`、`crm_migrator`，也没有验证 Local 固定持久目录或
S3 的完整 HTTPS 配置。角色复用和不完整对象配置可能在迁移后或真实业务写入时才暴露。

## 4. 本轮建议并纳入的增强

1. **可验证的导入进度**：按批次实际总量计算执行轮次，展示已处理/总量，并且只有数据库进入
   终态才显示完成；异常中断保持可继续执行。
2. **分层健康接口**：公网保留最小 liveness；详细 readiness 仅允许应用监听地址上的本机
   部署/运维探针使用。
3. **时区安全的日历窗口**：统一以用户时区生成月边界；返回 `total`/`truncated` 元数据并在
   UI 明确提示容量限制。
4. **可关联的安全错误诊断**：未捕获服务端异常写入不含业务数据的结构化事件，使用与客户端
   一致的 request ID。

不建议在本轮引入新的大型业务域或外部 AI 自动执行。现有客户 360、财务、隐私、导入、智能
建议、连接器和运维中心已经覆盖主要域；在没有真实供应商凭据、DPA、代表性数据和用户研究时，
扩大外部自动化会降低而不是提高可信度。

## 6. 审计执行后的关闭说明

上述 P1/P2/P3 项及四项增强已在 v3.1.0 中关闭。实施期真实数据库与 Chromium 验证又发现
资料 SELECT RLS 转换遗漏、迁移数量硬编码和已退休 QA helper 引用三项同源缺口，也已在
062 迁移、动态迁移计数及独立 TOTP QA 模块中关闭。补充部署审计发现的生产模板边界、
systemd 对象目录权限和弱角色/provider 预检，也已通过专用模板、共享配置策略、固定持久
沙箱目录及部署契约关闭。最终证据见
`FINAL_REAUDIT_2026-07-29_V3.1.0.md`。
